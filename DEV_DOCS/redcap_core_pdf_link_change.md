# Core change request: indirect PDF footer link annotations

## Summary

REDCap Core should emit its clickable `projectredcap.org` PDF footer link as an **indirect PDF annotation object** before the PDF finalization pipeline runs. Make the change in `Classes/PDF.php`; do not modify the PDF libraries under `Libraries/`. Keep the visible footer text and its `https://projectredcap.org` target.

## Current behavior and evidence

`PDF::setFooterImage()` renders the footer URL with a linked `Cell()` call. The URL has the HTTPS scheme; a trailing slash is not needed for this issue. The PDF library serializes that link dictionary directly inside the page's `/Annots` array.

During PDF Sealer development, an eConsent PDF signed with the direct footer link made Acrobat report that the certified document had changed. Removing the link made the certification clean but lost clickability. Moving the same link dictionary into an indirect object, while retaining the clickable footer and signing the resulting PDF, made Acrobat report no modification. The current sealer performs this conversion in its signing revision, and a newly generated eConsent PDF was confirmed in Acrobat as certified, unmodified, and still linked. These observations support an Acrobat interoperability fix; they do not establish that direct annotations violate the PDF specification.

## Scope of links found

In the current `Classes/PDF.php` rendering path, the footer `Cell()` call is the only active call found that supplies a URL to the PDF drawing API. `PDF::renderPDF()` also sends acknowledgement HTML to `WriteHTML()`. Both relevant `FPDF_HTML::WriteHTML()` implementations parse anchor tags, but their calls to `PutLink()` are commented out, so these anchors currently render as text rather than clickable PDF links. No other direct `Link()` calls were found in the Core classes/controllers searched. This finding concerns the standard `PDF.php` output path; it is not a guarantee about PDFs imported from elsewhere, generated by External Modules, or produced by unrelated PDF code.

## Requested Core behavior

1. Normalize Core-generated footer link annotations in `Classes/PDF.php` after the PDF library has serialized the document and before `PdfFinalizer::finalizeContents()` or any other consumer receives the bytes. Do this once per generated PDF, including paths that return a PDF string and paths that stream or store it. A PDF returned by `PDF::output(..., $returnString = true)` must also be normalized before its caller finalizes it.
2. Keep the existing footer text, HTTPS destination, and clickability. When the footer is suppressed by project configuration, do not add a link. On multipage PDFs, handle every page containing the footer.
3. Represent each affected link as an indirect annotation object referenced from the page's `/Annots` array. Preserve its rectangle, action, and other annotation entries. Preserve unrelated annotations and PDF structure. Reapplying the normalization should not duplicate links.
4. Perform this work before the finalization hook. Once a finalizer has sealed the PDF, Core must continue to store, hash, email, download, or expose exactly those finalized bytes.
5. Keep the implementation independent of the PDF Sealer EM and leave `Libraries/` untouched. Do not use a raw text replacement that assumes fixed PDF object numbers or that PDF strings cannot contain the same token sequence.

This may require a small PDF structure transformation in `PDF.php` after `Output(..., 'S')`. Unlike a change to the footer `Cell()` call alone, that transformation can control whether the serialized annotation is indirect. The implementation should first consolidate the relevant output paths so the normalization cannot be skipped or applied after sealing. The change request does not prescribe a particular parser or PDF revision strategy.

## Verification

- Generate one-page and multipage REDCap PDFs with the footer enabled and disabled; confirm the expected link count and that the enabled links open `https://projectredcap.org`.
- Inspect the resulting page `/Annots` arrays and confirm the footer links are indirect references, with no duplicate annotations and no lost unrelated annotations.
- Cover the PDF backends used for normal, Chinese, and Japanese project encodings, and the string-return, download, inline, and repository output paths.
- Run `qpdf --check` on the generated PDFs. Seal a fresh eConsent PDF and check that `pdfsig` verifies its signed bytes and Acrobat reports certification with no modifications while the footer link remains clickable.

## Compatibility

Keep PDF Sealer's `externalizeInlineLinks()` as a fallback for older REDCap-generated PDFs and other input PDFs containing direct links. Once the Core change is deployed and verified, the fallback should normally be a no-op for new `PDF.php` output.

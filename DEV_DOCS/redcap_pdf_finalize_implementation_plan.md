# `redcap_pdf_finalize` — Implementation Plan

## 1. Purpose

Introduce a new generic REDCap External Module hook:

```php
redcap_pdf_finalize(
    string $temporaryPdfPath,
    array $operation,
    array $context
): PdfFinalizeResult
```

The hook provides a controlled, ordered, transactional final-processing pipeline for PDFs generated by REDCap.

The hook is intentionally **fully generic**. REDCap Core and the External Module Framework must not encode assumptions about the purpose of a finalization operation. Cryptographic sealing is expected to be an important use case, but the hook must equally support watermarking, PDF/A conversion, metadata normalization, archival preparation, institution-specific processing, or future use cases not yet anticipated.

The central lifecycle guarantee is:

> After the `redcap_pdf_finalize` pipeline has completed, REDCap must store, hash, expose, email, archive, or otherwise use exactly the resulting PDF bytes without any subsequent byte-level modification.

---

## 2. Core lifecycle

The hook runs only after REDCap has completed all normal PDF generation and ordinary transformations.

Conceptually:

```text
Generate complete PDF
        ↓
All normal REDCap PDF construction
        ↓
All ordinary/non-final PDF transformations
        ↓
redcap_pdf_finalize execution pipeline
        ↓
PDF bytes become immutable
        ↓
edoc creation / hashing / storage / download / email / archive
```

For e-Consent PDFs, for example, the finalization pipeline must run only after REDCap has completed all applicable content such as:

- all pages;
- captured signature images;
- e-Consent audit content;
- headers and footers;
- merged attachments;
- PDF metadata;
- every other normal transformation.

No component may modify the PDF bytes after the finalization pipeline has completed.

---

## 3. Finalization operations are declared in `config.json`

An EM must explicitly declare every operation for which it wants `redcap_pdf_finalize` to be invoked.

Proposed structure:

```json
{
  "pdf-finalize": [
    {
      "id": "watermark",
      "purpose": "Add institutional watermark",
      "document_types": ["record_pdf", "survey_pdf", "econsent"],
      "is_terminal": false
    },
    {
      "id": "seal",
      "purpose": "Apply cryptographic document seal",
      "document_types": ["econsent"],
      "is_terminal": true
    }
  ]
}
```

Each declaration represents **one independently orderable operation and one possible hook invocation**.

An EM may declare any number of operations.

### 3.1 Required declaration fields

Each entry contains at least:

```text
id
purpose
document_types
is_terminal
```

#### `id`

A machine-readable identifier unique within the EM.

The globally meaningful identity of an operation is:

```text
module_prefix:operation_id
```

For example:

```text
watermarked_signatures:seal
institutional_watermark:watermark
```

Operation IDs are part of persisted project configuration and are therefore intended to be **stable API identifiers**. External Module Framework documentation must clearly state that changing an operation ID may make existing project execution-plan entries unresolved.

Human-facing text such as `purpose` may change without affecting stored execution plans.

#### `purpose`

Human-readable description of the operation, primarily intended for project designers.

The Framework does not interpret the purpose semantically.

#### `document_types`

An array of REDCap Core document-type identifiers for which the operation is applicable.

Example:

```json
["econsent", "record_pdf"]
```

The wildcard:

```json
["*"]
```

means that the operation applies to all document types.

The External Module Framework has **no semantic knowledge of document types**. REDCap Core owns and defines the concrete `document_type` vocabulary.

Framework documentation should list the currently known Core document types for EM developers and keep that documentation up to date, but Framework runtime behavior is limited to exact string matching and wildcard handling.

#### `is_terminal`

Boolean declaration specifying whether this operation is permitted to terminate the finalization pipeline.

```json
"is_terminal": true
```

means:

> This operation may return `terminal=true` at runtime.

It does **not** mean that every invocation must be terminal.

```json
"is_terminal": false
```

means:

> This operation must never return `terminal=true`.

---

## 4. `config.json` validation

Malformed finalization declarations must never become a project-level runtime state.

The existing External Module `config.json` validator must be extended to validate the `pdf-finalize` declaration structure before an EM can be enabled in the Control Center.

Validation must include at least:

- `pdf-finalize` has the expected structure;
- every operation has a non-empty `id`;
- operation IDs are unique within the module;
- `purpose` is present and valid human-readable text;
- `document_types` is present and structurally valid;
- document-type entries are valid strings;
- wildcard handling is structurally valid;
- `is_terminal` is a Boolean;
- unknown or malformed declaration data is handled according to established EM config validation rules.

An EM with an invalid `config.json` declaration must not be enableable.

Project-level UI therefore never needs a “malformed declaration” warning state.

---

## 5. Project execution plan

Projects store an explicit ordered list of finalization operations.

The persisted representation should be deliberately minimal:

```json
[
  "institutional_watermark:watermark",
  "archive_tools:normalize",
  "watermarked_signatures:seal"
]
```

Each entry consists only of:

```text
module_prefix:operation_id
```

Labels, document types, terminal capability, and other declaration metadata are always resolved dynamically from the currently installed/enabled EM and its current `config.json`.

This prevents stored project configuration from becoming a stale duplicate of module declarations.

---

## 6. One declaration = one pipeline entry = one hook invocation

If an EM declares multiple finalization operations, each operation is independently available in the project execution plan.

Example:

```json
{
  "pdf-finalize": [
    {
      "id": "watermark",
      "purpose": "Add verification watermark",
      "document_types": ["*"],
      "is_terminal": false
    },
    {
      "id": "seal",
      "purpose": "Apply cryptographic seal",
      "document_types": ["econsent"],
      "is_terminal": true
    }
  ]
}
```

The project may configure:

```text
1. watermarked_signatures:watermark
2. archive_tools:normalize
3. watermarked_signatures:seal
```

The same EM is therefore called twice for PDFs matching both declarations.

This permits operations from different EMs to be interleaved and avoids treating an entire module as either terminal or non-terminal.

---

## 7. Hook signature

The hook receives the complete resolved declaration entry as `$operation`:

```php
redcap_pdf_finalize(
    string $temporaryPdfPath,
    array $operation,
    array $context
): PdfFinalizeResult
```

For example:

```php
$operation = [
    'id' => 'seal',
    'purpose' => 'Apply cryptographic document seal',
    'document_types' => ['econsent'],
    'is_terminal' => true,
];
```

Passing the full declaration keeps the hook contract transparent, avoids requiring the EM to re-resolve its own declaration, and permits future declaration fields to become available without changing the hook signature.

`$operation` must represent exactly the Framework-resolved declaration for the pipeline entry being invoked.

---

## 8. Hook context

`$context` describes the REDCap PDF generation event.

It should contain enough information for generic EMs to determine whether and how to process the document.

A representative context is:

```php
[
    'document_type'       => 'econsent',
    'project_id'          => 123,
    'record_id'           => '10427',
    'event_id'            => 417,
    'instrument'          => 'consent',
    'repeat_instrument'   => null,
    'repeat_instance'     => null,
    'generation_reason'   => 'survey_completion',
    'generation_id'       => '...',
    'generated_at'        => '...',
    'suggested_filename'  => '...',
]
```

The exact set of fields may vary by PDF-generating Core pathway, but:

- `document_type` is required;
- `generation_id` should identify one PDF-generation/finalization lifecycle for correlation and logging;
- Core-specific context should be supplied where available;
- unavailable context should use a documented null/absence convention rather than invented values.

### 8.1 Context immutability

`$context` describes the original REDCap generation event.

It must not be mutated or accumulated by preceding finalization operations.

If cross-operation communication is ever required in the future, it should use a separate explicitly designed mechanism rather than modifying `$context`.

---

## 9. Document-type matching

The Framework invokes an operation only when its declaration matches the actual Core-supplied `document_type`.

Matching is generic:

```php
$matches =
    in_array('*', $operation['document_types'], true)
    || in_array($context['document_type'], $operation['document_types'], true);
```

If the operation does not match, it is skipped.

The Framework does not know or validate the semantics of concrete document-type identifiers beyond ordinary `config.json` structural validation.

REDCap Core controls which `document_type` is assigned to each generated PDF.

---

## 10. Result contract

Conceptually:

```php
final class PdfFinalizeResult
{
    public string $status;
    // modified | unchanged | failed

    public string $pdfPath;

    public bool $terminal = false;

    public array $metadata = [];

    public ?string $errorCode = null;
    public ?string $errorMessage = null;
}
```

The concrete implementation may use the Framework's preferred result/value-object conventions, but the semantics must remain equivalent.

### 10.1 `modified`

The operation successfully produced a PDF that should become the current artifact for subsequent pipeline operations.

### 10.2 `unchanged`

The operation successfully completed without changing the PDF.

`unchanged` together with:

```php
terminal = true
```

is valid when the declaration allows terminal behavior.

An operation may inspect the artifact, decide that it already satisfies its required terminal condition, and intentionally stop further processing without changing bytes.

### 10.3 `failed`

The operation failed in a controlled manner.

Its working output must not be adopted.

An uncaught `Throwable` is treated equivalently to `failed` for pipeline purposes.

---

## 11. Transactional operation execution

Every individual finalization operation must be transactional.

The Framework, not the EM, owns the safe working-copy lifecycle.

Conceptually:

```text
current PDF
    ↓
Framework creates working copy
    ↓
invoke one operation on working copy
    ↓
validate result and contract
    │
    ├─ accepted → adopt operation result as current PDF
    │
    └─ failed/invalid → discard operation result
                        keep previous current PDF
    ↓
continue unless an accepted result is terminal
```

An EM must never receive the only valid copy of the current artifact.

This guarantees that:

- a failed operation does not destroy a valid PDF;
- a partially modified/corrupted working file is not adopted;
- failure of a later operation does not undo successful earlier operations.

Example:

```text
Original PDF
    ↓
Watermark succeeds
    ↓
Current = watermarked PDF
    ↓
Metadata operation fails
    ↓
Current remains watermarked PDF
    ↓
Seal succeeds
    ↓
Current = sealed watermarked PDF
```

The pipeline does **not** revert to the original PDF merely because a later operation fails.

---

## 12. Runtime contract enforcement

The Framework must verify that runtime behavior is permitted by the operation declaration.

The critical rule is:

```text
declaration: is_terminal = false
runtime:     terminal = true
```

This is a Framework contract violation.

The result of that invocation must:

- be discarded;
- not become the current PDF;
- not terminate the pipeline;
- be logged as an operation failure/contract violation;
- leave the previously accepted current PDF intact;
- allow subsequent pipeline operations to continue.

Conversely:

```text
declaration: is_terminal = true
runtime:     terminal = false
```

is valid.

A terminal-capable operation is permitted, but not required, to terminate a particular invocation.

---

## 13. Terminal semantics

`terminal=true` means only:

> Stop invoking further `redcap_pdf_finalize` operations for this PDF.

It does not itself mean that the PDF lifecycle has already been committed.

Terminality takes effect only when the result has otherwise been successfully validated and adopted.

Therefore:

- `failed + terminal=true` does not terminate;
- an exception does not terminate;
- a contract-violating `terminal=true` does not terminate;
- only an accepted successful result may terminate the pipeline.

Once the pipeline either:

1. exhausts all matching configured operations, or
2. stops after an accepted `terminal=true` result,

REDCap crosses the true lifecycle boundary:

> The PDF bytes are now final and immutable.

No subsequent REDCap or EM processing may alter them.

Only byte-preserving operations may follow, such as:

- hashing;
- edoc creation;
- repository storage;
- audit association;
- download delivery;
- email attachment creation;
- archival copying.

---

## 14. User-controlled ordering

The External Module Framework must not define or infer a global priority scheme for PDF finalizers.

Order is explicit project configuration.

This is necessary because:

- operation order can materially change output;
- the same EM may expose several operations with different semantics;
- an EM may be terminal only for some operations/document types;
- project requirements differ;
- Core/Framework cannot safely infer domain-specific intent.

The Framework may detect potentially surprising consequences, but it must not prohibit project designers from choosing an order.

---

## 15. Potentially unreachable operations

A configured order such as:

```text
1. signing:seal
   terminal for econsent

2. watermark:add
   applies to econsent
```

is allowed.

The UI should warn that the later operation is potentially unreachable for overlapping document types.

It must **not** reject the configuration.

Static declarations describe possible behavior, not guaranteed runtime behavior. The first operation may legitimately return `terminal=false`, allowing the later operation to run.

Warnings are therefore advisory.

---

## 16. Missing or unavailable pipeline entries

A stored entry may become unresolved because, for example:

- the EM is temporarily disabled;
- the EM is no longer installed;
- an operation ID was removed or renamed in a later EM version;
- a project was copied/restored on another REDCap instance without the same EM set.

Example stored entry:

```text
old_signing_module:seal
```

If the pair cannot currently be resolved:

1. log a warning;
2. skip the entry at runtime;
3. retain the stored entry unchanged;
4. continue processing later entries;
5. show the unresolved entry visibly in the project execution-plan UI.

The Framework must **not automatically remove unresolved entries**.

This preserves project-designer intent and permits normal behavior to resume if the EM or operation later becomes available again.

---

## 17. Dynamic re-evaluation after EM changes

The persisted pipeline represents project intent.

Current `config.json` declarations represent currently available capabilities.

Warnings represent the relationship between those two states.

Therefore:

```text
stored pipeline       = project-designer intent
current declarations  = current EM capabilities
warnings              = current compatibility/consequences
```

Warnings and operation resolution should be re-evaluated dynamically:

- when the execution-plan UI is opened;
- before the pipeline is executed;
- after module enable/disable changes;
- after module upgrades where declarations may have changed.

The stored pipeline must not be silently rewritten merely because current declarations changed.

---

## 18. Duplicate operation occurrences

The same operation may appear more than once in a project execution plan.

Example:

```text
watermark:add
archive:normalize
watermark:add
```

The Framework must not assume operations are idempotent or non-repeatable.

For `redcap_pdf_finalize`, multiple assignment is allowed.

The UI may indicate that an operation is used more than once, but this is not an error.

Each occurrence results in a separate hook invocation when its `document_types` declaration matches.

---

## 19. Project enablement behavior

When enabling an EM that declares finalization operations, the Framework must avoid silently making ordering decisions that could affect existing PDF behavior.

If the project already has a `redcap_pdf_finalize` execution plan and a newly enabled EM introduces additional available operations, project-level enablement must include explicit configuration of where the new operations belong when they are to be used.

The key principle is:

> The Framework must not silently insert newly introduced operations into an existing project pipeline at an inferred priority.

Where appropriate, enablement can transition directly into the execution-order editor.

---

## 20. Control Center “enable for all projects”

A Control Center action that makes an EM active/available globally must not silently introduce unresolved ordering into projects that already use `redcap_pdf_finalize`.

For each affected project:

- if no project-specific pipeline interaction requires a placement decision, normal enablement may proceed;
- if enabling the EM would require inserting one or more new operations into an existing pipeline, the EM must remain disabled for that project;
- that project requires manual per-project activation and explicit placement/order configuration.

The Control Center should report projects that were not automatically activated because project-specific finalization ordering is required.

This behavior is especially important for terminal-capable operations, but the rule is generic and applies to all finalization operations.

---

## 21. Project copy, template, migration, and restore behavior

The execution plan is project configuration and should follow the established REDCap/EM semantics for copying or migrating project-level External Module configuration.

Unresolved operation entries must be retained after copy/restore/migration.

This allows a project copied to another instance to preserve its intended pipeline even if the destination temporarily lacks one or more contributing EMs.

The normal unresolved-entry warning behavior then applies.

---

## 22. Safe PDF path handling

The Framework must control temporary file handling.

A finalizer must not be able to cause arbitrary filesystem content to be adopted as a PDF merely by returning an unrestricted path.

The implementation should prefer one of these models:

1. require modification/replacement of a Framework-created working file; or
2. permit another result path only within a Framework-controlled temporary area.

Before adopting a result, the Framework should at minimum verify that it:

- exists;
- is readable;
- is non-empty;
- is plausibly a PDF;
- resides in an allowed location according to the chosen temporary-file contract.

Exact PDF structural validation may use existing REDCap facilities where available.

---

## 23. Failure behavior

A failed finalization operation must not prevent REDCap from storing an otherwise valid PDF.

For each operation failure:

- discard that operation's output;
- retain the previously accepted current PDF;
- log the failure;
- continue to the next applicable operation unless processing was already validly terminated earlier.

An uncaught exception must be caught at the Framework boundary and handled equivalently.

This means that a pipeline such as:

```text
watermark        → success
metadata         → failure
cryptographic seal → success / terminal
```

can still result in a valid watermarked and sealed artifact.

Use-case-specific EMs may implement additional warnings or durable status records through their own EM facilities.

---

## 24. Result metadata

`PdfFinalizeResult` may return operation-specific metadata.

Example:

```php
[
    'seal_status' => 'sealed_bt',
    'timestamp_source' => 'external_rfc3161',
]
```

The Framework may use metadata for execution logging/diagnostics.

It should not automatically turn arbitrary result metadata into permanent generic REDCap storage.

An EM that requires durable application-specific state should persist that state using normal EM mechanisms.

Metadata should be associated with the specific operation occurrence and generation ID in logs where practical.

## 25. Generation correlation and logging

Each PDF generation/finalization lifecycle should have a correlation identifier, exposed as:

```php
$context['generation_id']
```

Framework logging should make it possible to reconstruct the pipeline for a generated PDF.

Conceptually:

```text
generation_id = abc123

institutional_watermark:watermark
    matched / invoked
    modified
    success

archive_tools:normalize
    matched / invoked
    failed

watermarked_signatures:seal
    matched / invoked
    modified
    success
    terminal

final artifact
    stored as edoc 91827
```

Logging should distinguish at least:

- skipped because document type did not match;
- unavailable/unresolved entry;
- invoked unchanged;
- invoked modified;
- controlled failure;
- uncaught exception;
- contract violation;
- accepted terminal result;
- final artifact commit.

Not every step necessarily needs to become a REDCap user-facing audit-trail event. Framework/system logging may be sufficient, depending on existing conventions.

## 27. Reusable UI component as a design goal

The ordered-assignment UI required by this feature should be implemented with **flexibility and reuse as an explicit design goal**.

It should not be intrinsically tied to:

- PDF finalization;
- `redcap_pdf_finalize`;
- document types;
- terminal operations;
- or necessarily even to hook configuration.

The design should allow consuming features to provide behavior such as:

- item labels/rendering;
- assignability rules;
- whether multiple assignment is permitted;
- state/use-count information;
- state-dependent styling;
- warnings;
- other feature-specific presentation or validation data.

However, the detailed generic component API is **intentionally deferred**.

The implementation of `redcap_pdf_finalize` should require only the concrete functionality needed by this feature while avoiding design decisions that would prevent later reuse for:

- future ordered hooks;
- existing hooks such as `redcap_pdf`;
- other Framework features requiring ordered assignment from an available-item catalog.

## 28. Separation of responsibilities

### REDCap Core

Responsible for:

- generating the complete PDF;
- defining and assigning `document_type`;
- supplying Core generation context;
- invoking the Framework finalization pipeline at the correct lifecycle point;
- guaranteeing no byte-level PDF modification after finalization;
- using the final exact bytes for edoc creation, hashing, storage, delivery, and archival.

### External Module Framework

Responsible for:

- `config.json` schema validation;
- resolving operation declarations;
- storing project execution plans;
- matching `document_type` and `*`;
- ordered invocation;
- working-copy transactionality;
- runtime contract enforcement;
- terminal pipeline control;
- exception/failure isolation;
- unresolved-entry handling;
- logging;
- project-order configuration UI;
- safe temporary-file handling.

The Framework does **not** interpret operation purposes or concrete document-type semantics.

### External Module

Responsible for:

- declaring operations accurately;
- keeping operation IDs stable;
- implementing each declared operation when invoked;
- returning valid `PdfFinalizeResult` data;
- never returning `terminal=true` from a declaration with `is_terminal=false`;
- storing any use-case-specific durable status through normal EM mechanisms;
- not relying on post-finalization mutation of the PDF.

## 29. Reference runtime algorithm

Conceptually:

```php
$pdf = $coreGeneratedPdf;
$generationId = createGenerationId();

foreach ($projectExecutionPlan as $entry) {

    $declaration = resolveOperationDeclaration($entry);

    if ($declaration === null) {
        logWarning($generationId, $entry, 'operation_unavailable');
        continue;
    }

    if (!matchesDocumentType(
        $context['document_type'],
        $declaration['document_types']
    )) {
        logSkipped($generationId, $entry, 'document_type_mismatch');
        continue;
    }

    $workingPdf = createFrameworkWorkingCopy($pdf);

    try {
        $result = invokeRedcapPdfFinalize(
            $workingPdf,
            $declaration,
            $context
        );
    }
    catch (\Throwable $e) {
        discardWorkingCopy($workingPdf);
        logFailure($generationId, $entry, $e);
        continue;
    }

    if ($result->status === 'failed') {
        discardOperationResult($result, $workingPdf);
        logFailure($generationId, $entry, $result);
        continue;
    }

    if ($result->terminal && !$declaration['is_terminal']) {
        discardOperationResult($result, $workingPdf);
        logContractViolation(
            $generationId,
            $entry,
            'terminal_not_declared'
        );
        continue;
    }

    if ($result->status === 'modified') {
        if (!validateReturnedPdf($result->pdfPath)) {
            discardOperationResult($result, $workingPdf);
            logFailure($generationId, $entry, 'invalid_pdf_result');
            continue;
        }

        $pdf = adoptOperationResult($result->pdfPath);
    }
    else {
        discardUnusedWorkingCopy($workingPdf);
    }

    logSuccess($generationId, $entry, $result);

    if ($result->terminal) {
        break;
    }
}

// Hard lifecycle boundary:
// from this point onward the bytes must never be modified.
commitExactPdfBytes($pdf);
```

The exact implementation should use established REDCap/Framework conventions rather than necessarily mirroring this pseudocode literally.

## 32. Example: advisory unreachable warning

Configured pipeline:

```text
1. signing:seal
   document_types = ["econsent"]
   is_terminal = true

2. watermark:add
   document_types = ["econsent", "record_pdf"]
   is_terminal = false
```

The UI may show:

```text
2. watermark:add
   ⚠ Potentially unreachable for econsent because the preceding
     signing:seal operation may terminate processing.
```

The project designer may save this order.

At runtime:

- if `signing:seal` returns `terminal=true`, `watermark:add` is not called;
- if `signing:seal` returns `terminal=false`, `watermark:add` is called normally.

## 35. Acceptance criteria

The implementation is complete when all of the following are true:

1. An EM can declare one or more independent `redcap_pdf_finalize` operations in `config.json`.
2. Invalid declarations prevent EM enablement through existing config validation.
3. Each declared operation is independently orderable in project configuration.
4. Stored execution plans use `module_prefix:operation_id`.
5. Multiple occurrences of the same operation are supported.
6. Multiple operations from the same EM result in separate hook calls.
7. The hook receives the full declaration entry as `$operation`.
8. The Framework calls an operation only for matching `document_type` values or `*`.
9. The Framework itself has no semantic knowledge of concrete document types.
10. Operations execute in explicit project-defined order.
11. Each operation is transactionally isolated by Framework-controlled working copies.
12. Failure or exception preserves the previously accepted PDF and does not prevent later operations.
13. A non-terminal declaration returning `terminal=true` is rejected, discarded, logged, and does not stop the pipeline.
14. A terminal-capable operation may validly return `terminal=false`.
15. An accepted `unchanged + terminal=true` result is permitted.
16. Only an accepted successful terminal result stops the pipeline.
17. Missing/unavailable stored entries are warned about, skipped, retained, and never silently deleted.
18. Potentially unreachable operations generate advisory UI warnings but are not prohibited.
19. REDCap never silently infers operation order when introducing operations into an existing pipeline.
20. Control Center global enablement does not silently create project-specific ordering.
21. The project UI supports drag/drop assignment and ordering, deletion, duplicate use, use-state display, and unresolved-entry warnings.
22. The UI implementation is designed with future reuse in mind without over-specifying the generic component API now.
23. After the pipeline completes, REDCap performs no further byte-level modification of the PDF.
24. Edoc creation, hashing, storage, download, email, and archival use exactly the finalized PDF bytes.
25. Logging permits a generated artifact's finalization path to be reconstructed through a correlation/generation ID.

## 36. Architectural summary

The design deliberately separates three concepts:

```text
config.json declaration
    = what an operation may do

project execution plan
    = when operations should be attempted

runtime hook result
    = what actually happened
```

REDCap Core owns PDF generation and document-type semantics.

The External Module Framework owns declaration validation, ordered transactional execution, configuration, contract enforcement, and lifecycle safety.

External Modules own the actual processing logic.

The result is a generic final-PDF processing primitive that supports composable workflows such as:

```text
watermark
    ↓
metadata normalization
    ↓
cryptographic seal [TERMINAL]
```

without REDCap Core needing to know what a watermark, seal, PDF/A conversion, archival transform, or any future operation actually means.
